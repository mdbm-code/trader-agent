Контекст

Sprint 01 закрыт: есть сервер, токены песочницы, один smoke-скрипт на чистом JS
(scripts/smoke.mjs). Кода на TypeScript в проекте пока нет вообще — ни tsconfig.json,
ни src/, ни зависимостей (tsx, vitest, zod не установлены). .nvmrc отсутствует,
хотя документация Sprint 01 на него ссылается.

Согласно docs/ROADMAP.md, Sprint 02 должен дать:
- tsconfig.json, скрипты typecheck/test/dev, зависимости tsx, vitest, zod;
- src/shared: Money и Quantity (с тестами), Clock, Logger, EventBus, конфиг;
- систему ошибок: AppError, ErrorReporter (Композит), приёмник в консоль, ограничитель
  повторов, маскировка секретов, installProcessGuards;
- порты и доменные типы модулей; заглушки identity, tenancy, signals, billing,
  каналов уведомлений;
- composition-root.ts, main-worker.ts, smoke-тест на новой архитектуре;
- ADR 001–010.

Критерий готовности спринта: typecheck и test зелёные; искусственно брошенное
исключение в main-worker попадает в консоль в едином формате, токен в тексте ошибки
замаскирован.

Я проверил ARCHITECTURE.md на предмет уже закреплённой нумерации ADR (grep -n -i "ADR")
— фиксированных номеров там нет, только формат имени файла NNN-название.md (раздел 13).
Значит нумерацию 001–010 ниже я предлагаю сам, её нужно подтвердить со студентом перед
записью ADR (по правилу CLAUDE.md п.4 — решение, которого нет в документах, сначала
обсуждаем).

Важное сужение объёма (тоже требует подтверждения студента). Пункт ROADMAP «порты и
доменные типы всех модулей» противоречит принципу YAGNI из раздела 11 архитектуры
(«не заглушаем внутренности, пока до них не дошли»). В сквозной сценарий Sprint 02 явно
входят только 4 модуля с меткой 🧩 (identity, tenancy, signals, billing) и каналы
уведомлений — они называются в легенде ROADMAP как «заложенные заглушками именно в
Sprint
02». Модули market-data, brokerage, strategies, backtesting, risk, trading,
intelligence получат свои порты в сприntах, где реально появится первый потребитель
(Sprint 03–07 по ARCHITECTURE.md разделу 7). План ниже реализует суженный вариант —
это стоит проговорить со студентом как маленькое архитектурное решение перед стартом
урока 12.

Порядок уроков — от инструментов к сборке приложения, как просил студент. Каждый урок —
это один цикл «План → Код (1–3 файла) → Путеводитель → Стоп» из режима «Разбор».

Урок 1 — TypeScript-контур проекта

Цель. Рабочий тулчейн: tsc, tsx, vitest — фундамент для всех следующих уроков.

Паттерн/принцип. Без ООП-паттерна: принцип «typecheck и тесты — обязательный контур
обратной связи», аналог в 1С — синтаксический контроль конфигурации перед запуском.

Файлы.
- package.json — правка: devDependencies (typescript, tsx, vitest, zod,
  @types/node), скрипты typecheck (tsc --noEmit), test (vitest run --passWithNoTests,
  пока нет тестов), dev (tsx --env-file=.env ...).
- tsconfig.json — новый: strict: true, модульная система под "type": "module"
  (module/moduleResolution: NodeNext).
- .nvmrc — новый: 24 (устраняет расхождение с документом Sprint 01).

Результат. npm install, npm run typecheck, npm test, npm run dev выполняются
без ошибок (тестов ещё нет — это нормально).

Проверка. Показать вывод всех команд студенту; убедиться, что node_modules/vitest
и node_modules/typescript появились, tsc --noEmit не падает на пустом src/.

Урок 2 — AppError и порт ErrorReporter

Цель. Заложить фундамент системы ошибок до того, как он понадобится Money и другим
модулям (у нас правило: ошибки — только наследники AppError).

Паттерн/принцип. Абстрактный базовый класс (различаем операционные и программные
ошибки — раздел 15 архитектуры); Порт (ErrorReporter — интерфейс, который знает домен,
не знает деталей отправки).

Файлы.
- src/shared/errors/app-error.ts + app-error.test.ts — абстрактный класс AppError
  (code, severity, transient, context, cause), пара конкретных наследников для
  теста (например, ExternalServiceError, ConfigError).
- src/shared/errors/error-reporter.ts — порт ErrorReporter, тип ErrorEvent, порт
  ErrorSink.

Результат. Тесты подтверждают: name наследника выставляется автоматически
(new.target.name), context неизменяем, cause пробрасывается.

Проверка. npm run typecheck && npm test зелёные; студент объясняет своими словами,
зачем code и severity — машине и человеку соответственно.

Урок 3 — CompositeErrorReporter и приёмник в консоль

Цель. Одна ошибка уходит сразу во все приёмники; пока приёмник один — консоль.

Паттерн/принцип. Композит (CompositeErrorReporter реализует ErrorReporter, внутри
— список ErrorSink, Promise.allSettled, чтобы сбой одного приёмника не мешал другим).

Файлы.
- src/shared/errors/composite-error-reporter.ts + тест.
- src/shared/errors/console-error-sink.ts + тест.

Результат. CompositeErrorReporter с одним ConsoleErrorSink печатает ошибку в
едином формате (код, severity, сообщение, context).

Проверка. Тест на то, что при падении одного приёмника (мок, бросающий исключение)
второй всё равно получает событие. Вопрос на понимание: почему report() сам никогда не
бросает исключение?

Урок 4 — Ограничитель повторов и маскировка секретов

Цель. Не заваливать канал оповещений одинаковой ошибкой; не пропускать токены в текст.

Паттерн/принцип. Декоратор (RateLimitedErrorReporter оборачивает ErrorReporter,
добавляя поведение «не чаще раза в N минут, дальше — агрегация „повторилась 37 раз“»)
плюс чистая функция маскировки (maskSecrets).

Файлы.
- src/shared/errors/rate-limited-error-reporter.ts + тест (с FakeClock — тест уже
  показывает, зачем нужен порт времени из урока 8, если урок 8 ещё не пройден — можно
  временно передать простую тестовую реализацию Clock, а не полноценный FakeClock).
- src/shared/errors/mask-secrets.ts + тест (маскирует t.xxxx…-подобные строки).

Результат. Дубли ошибок за короткое окно не уходят повторно; текст с токеном в логе
замаскирован.

Проверка. Тест: 10 одинаковых ошибок подряд → 1 реальная отправка + агрегированное
сообщение о повторах. Обсудить со студентом: не издержки ли декоратор поверх декоратора
—
где граница, что считаем «одинаковой» ошибкой (по code? по code + message?).

Урок 5 — installProcessGuards и NotImplementedError

Цель. Программные ошибки на уровне процесса не должны оставлять процесс в недостоверном
состоянии; заглушки должны честно падать понятной ошибкой, а не молчать.

Паттерн/принцип. Разница операционных/программных ошибок на практике; принцип YAGNI
для заглушек (раздел 11).

Файлы.
- src/app/process-guards.ts — installProcessGuards(reporter): uncaughtException →
  отчёт + process.exit(1) (PM2 перезапустит), unhandledRejection → отчёт без выхода.
- src/shared/errors/not-implemented-error.ts + тест — наследник AppError,
  code: 'NOT_IMPLEMENTED', принимает what и plannedSprint.

Результат. Пригодится в уроке 12 (main-worker) и уроке 12′ (заглушки модулей).

Проверка. Ручная проверка: временно бросить исключение в тестовом скрипте и увидеть
вызов reporter.report с source: 'uncaughtException' (мок вместо реального
ErrorReporter). Настоящую сквозную проверку делаем в уроке 13.

Урок 6 — Money: первый объект-значение

Цель. Деньги как immutable value object на bigint, без ошибок плавающей точки.

Паттерн/принцип. Value Object (раздел 7.2): приватный конструктор, только фабричные
методы, операции возвращают новый объект, инвариант «нельзя сложить рубли с долларами».

Файлы.
- src/shared/money/money.ts + money.test.ts: nano: bigint, currency: string,
  Money.fromQuotation(...), Money.zero(currency), add, subtract, assertSameCurrency.

Результат. Тесты: add не мутирует исходный объект; несовпадение валют — ошибка.

Проверка. Обсудить со студентом до кода (важный момент для «Плана» этого урока):
пример в ARCHITECTURE.md (строка 377) для несовпадения валют бросает голый Error, а
правило CLAUDE.md требует наследников AppError для всех ошибок. Это надо решить вместе —
скорее всего заводим CurrencyMismatchError extends AppError — и внести в ADR (см. урок
14).
Вопрос на понимание: почему у Money приватный конструктор?

Урок 8 — Clock: порт времени

Цель. Убрать new Date() из ядра — торговые инварианты требуют управляемого времени
(инвариант №5, раздел 10), бэктест должен уметь «перематывать» время.

Паттерн/принцип. Порт + два адаптера: SystemClock (реальное время) и FakeClock
(управляемое время для тестов — Test Double, но не мок, а полноценная реализация порта).

Файлы.
- src/shared/time/clock.ts — интерфейс Clock { now(): Date } + SystemClock.
- src/shared/time/fake-clock.ts + тест — FakeClock с методом advance(ms).

Результат. Тест показывает, как FakeClock использовать в чужом тесте (например,
переиспробовать в тесте из урока 4 для ограничителя повторов).

Проверка. Вопрос: почему FakeClock — не мок-библиотека (vi.fn()), а обычный класс?

Урок 9 — Logger: порт логирования

Цель. Единый интерфейс логирования вместо разбросанных console.log.

Паттерн/принцип. Порт + адаптер (ConsoleLogger), минимальный — без стратегий уровней
сверх необходимого (YAGNI: не делаем ротацию файлов, транспорт в файл и т.п. сейчас).

Файлы.
- src/shared/logging/logger.ts — интерфейс Logger { debug/info/warn/error(...) }.

Результат. ConsoleLogger(cfg.logLevel) фильтрует сообщения ниже настроенного уровня.

Урок 10 — EventBus: Наблюдатель

Цель. Разъединить модули: издатель события не знает подписчиков.

Паттерн/принцип. Наблюдатель / шина событий (раздел 7.8, аналог в 1С — подписки на

Файлы.

Урок 11 — AppConfig: конфигурация из .env

Цель. Один явный объект конфигурации вместо разбросанных process.env.X по всему
коду; невалидный .env должен падать сразу при старте, а не посреди торгового дня.

Паттерн/принцип. Fail fast на границе процесса; zod-схема как явный контракт
(словарь 1С, раздел 20, ближайший аналог — проверка заполненности реквизитов при
записи).

Файлы.
- src/shared/config/app-config.ts + тест — zod-схема, loadConfig(env): AppConfig,
  ошибка валидации — ConfigError extends AppError (уже есть из урока 2).
- .env.example — обновить список переменных под схему.

Результат. Тест: отсутствие обязательной переменной → ConfigError с понятным
сообщением, без утечки значений остальных переменных в текст ошибки.

Проверка. Ручная проверка маской (sed -E 's/=(.{6}).*/=\1…/' .env), что схема не
требует ничего, чего нет в реальном .env — не открывать сам .env.

Урок 12 — Заглушки модулей: identity, tenancy, signals, billing, уведомления

Цель. Заложить границы будущих модулей портами и честными заглушками, не строя лишнего
(YAGNI, раздел 11) — до старта нужно подтвердить со студентом сужение объёма (см.
«Контекст»).

Паттерн/принцип. Заглушка = интерфейс + класс, кидающий NotImplementedError с
указанием планового спринта. Один и тот же приём применяется 4+ раза подряд — если
студент
захочет, после первых двух модулей это отличный момент предложить «Лестницу, уровень 2»
(написать заглушки для signals/billing самому по образцу).

Файлы (по одному порту на модуль, группируем в 2 подурока по 2 модуля):
- 12a: src/modules/identity/* (UserRepository, PasswordHasher, TokenIssuer —
  порты) + src/modules/tenancy/* (TenantRepository, SecretVault), каждый модуль —
  свой index.ts как публичный API.
- 12b: src/modules/signals/* (SubscriptionRepository, DeliveryQueue) +
  src/modules/billing/* (PaymentProvider, PlanRepository) + один канал уведомлений
  (SmsChannel implements NotificationChannel, пример из архитектуры раздел 11,
  дословно).

Результат. Каждый порт — только тип; каждая заглушка — вызывает NotImplementedError
с корректным номером спринта (свериться с ROADMAP: identity/tenancy/signals/billing —
какие спринты, SmsChannel — Sprint 15 по примеру из архитектуры).

Проверка. Тест на 1–2 заглушки: вызов метода бросает NotImplementedError с ожидаемым
code. typecheck проходит — значит порты синтаксически согласованы с доменными типами,
которые они объявляют.

Файлы.

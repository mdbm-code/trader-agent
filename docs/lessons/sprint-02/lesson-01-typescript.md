# Урок 1 (Sprint 02) — TypeScript-контур

## Что построили

| Файл | Роль |
|---|---|
| `.nvmrc` | Фиксирует версию Node (`24`) для `nvm use`/`nvm install`. |
| `tsconfig.json` | Настройки компилятора: strict-режим, `NodeNext`, `noEmit` — `tsc` только проверяет типы, не собирает код. |
| `package.json` (правки) | Скрипты `typecheck`/`test`/`dev`, `devDependencies`: `typescript`, `tsx`, `vitest`, `@types/node`. |
| `src/app/main-worker.ts` | Заготовка точки входа торгового процесса. Наполняется в уроке 13 (Composition Root). |
| `tests/sanity.test.ts` | Временный тест, доказывающий, что vitest настроен. Удаляется в уроке 2. |
| `docs/architecture/adr/001-typescript.md` | Первый ADR проекта: почему TypeScript, а не JS. |

## Ключевые решения и почему

- **TypeScript strict, без шага сборки** — код выполняется через `tsx`, типы проверяет отдельно
  `tsc --noEmit`. Обоснование и альтернативы — [ADR 001](../../architecture/adr/001-typescript.md).
- **`allowImportingTsExtensions: true`** в `tsconfig.json` — при `NodeNext` относительные импорты
  по умолчанию требуют расширение `.js` (так резолвит ESM сам Node), даже если исходник `.ts`.
  Флаг разрешает писать честное `.ts`. Допустим только вместе с `noEmit` — у нас так и есть.
- **`zod` не ставим** — первый импорт будет в уроке 11 (`AppConfig`), тащить зависимость заранее
  незачем (YAGNI).
- **ADR 001 создан именно в этом уроке**, а не отложен до урока 14 — по собственному же правилу
  спринта: «ADR пишем в уроке, где принимается решение; урок 14 — сверка и закрытие»
  (`docs/sprints/sprint-02-plan.md`).

## Что пошло не так и чему научились

Версии пакетов в `package.json` изначально были прописаны по памяти
(`typescript ^5.7`, `vitest ^2.1`, …), без проверки. Результат:

1. `npm audit` после первой установки показал 5 уязвимостей (включая critical) — в
   транзитивной цепочке `vitest@2.x → vite → esbuild` была дыра в dev-сервере.
2. Поднял версии до актуальных (`npm view <пакет> version`), но повторный `npm install` упал с
   `ERESOLVE`: `package-lock.json`, созданный первой установкой, всё ещё держал старый
   `vitest@2.1.9`, который конфликтовал по peer-зависимости `vite` с новым `vitest@5`.
3. Починил через `rm -rf node_modules package-lock.json && npm install` — чистая установка,
   `0 vulnerabilities`.

**Вывод, зафиксированный в `CLAUDE.md`:** версии пакетов — только после проверки через
`npm view`, не по памяти; `@types/node` — в мажорной линии установленного Node, а не последняя
из существующих (иначе типы могут не совпадать с реально установленным Node.js).

## Вопросы и ответы

**Контрольный вопрос.** `tsc --noEmit` и `tsx watch` читают один и тот же файл — но `dev`
не спотыкается об ошибки типов, которые ловит `typecheck`. Почему?

> `tsx` работает через `esbuild`, который транспилирует TypeScript в JavaScript **файл за
> файлом**: вырезает аннотации типов, не строя граф типов по всему проекту. Он физически не
> может заметить ошибку вроде «сюда передали не тот тип» — для этого нужно прочитать определение
> из другого файла. `tsc`, наоборот, читает проект целиком и проверяет типы, но (с `noEmit`)
> ничего не запускает. Отсюда практическое следствие: **зелёный `npm run dev` не значит
> корректный код** — перед коммитом обязателен `npm run typecheck`.

**Почему `tsx` в `devDependencies`, если в проде PM2 будет запускать робота тем же `tsx`?**
Формально нестыковка: `devDependencies` не ставятся при `npm ci --omit=dev`, а `tsx` в нашей
схеме нужен и во время исполнения, не только разработчику. Сейчас это не ломается только потому,
что нигде не делаем `--omit=dev`. Решение отложено до урока 13 — записано в открытых вопросах
плана спринта.

**А в продакшене `tsx watch` тоже?** Нет: `watch` (пересборка при изменении файла) имеет смысл
только для разработки. В проде — обычный запуск без `watch` (что именно это будет за команда,
решится в уроке 13 вместе с `composition-root.ts`).

**Почему в коммите `build:`, а не `feat:`?** Conventional Commits резервирует `feat:` за
изменениями, которые добавляют функциональность продукта — то, что увидит пользователь кода
(в этом проекте — следующие уроки: `AppError`, `Money`, коннектор и т.д.). Урок 1 не добавляет
торговой логики: меняются только `package.json`/`tsconfig.json` и зависимости сборки/проверки.
Это ровно то, что тип `build` описывает по спецификации — изменения системы сборки и внешних
зависимостей. `feat:` придержим до урока 2, где появится первый настоящий класс (`AppError`).

## Новые термины (аналогии из 1С)

| Термин | Смысл | Аналогия 1С |
|---|---|---|
| **strict-режим TypeScript** | Компилятор проверяет `null`/`undefined`/неявный `any` | Жёсткая типизация реквизитов, а не «Произвольное» везде |
| **`tsc --noEmit`** | Компилятор используется только как чекер, без сборки | «Проверка модулей конфигурации» — отдельное, медленное действие по требованию |
| **`tsx`** | Быстрый запуск TS-файла без проверки типов (через esbuild) | «Выполнить» обработку из конфигуратора — платформа не гоняет полную проверку перед запуском |
| **ADR (Architecture Decision Record)** | Отдельный документ: контекст → решение → альтернативы → последствия | Запись в регламенте/ТЗ, почему выбрано конкретное техническое решение, а не просто факт в коде |
| **`devDependencies` / `dependencies`** | Нужно только на этапе разработки vs нужно во время исполнения | Внешняя обработка для разработчика (не входит в конфигурацию пользователя) vs общий модуль, зашитый в саму конфигурацию |
| **lockfile (`package-lock.json`)** | Фиксирует точные версии всего дерева зависимостей | Список версий расширений/библиотек, зафиксированный вместе с конфигурацией, чтобы у всех была одна и та же сборка |
| **Conventional Commits** | Префикс коммита (`feat`/`build`/`docs`/…) говорит о типе изменения | Вид документа в системе версионирования конфигурации: «новая функциональность» vs «исправление» vs «технические работы» |

## Как проверить самому

```bash
npm run typecheck   # tsc --noEmit — не должно быть ошибок
npm run test         # vitest run — 1 тест проходит (sanity.test.ts)
npm run dev           # tsx watch — печатает "trader-agent: dev-контур жив", Ctrl+C для остановки
npm audit             # 0 vulnerabilities
cat .nvmrc            # 24
node -v                # должна совпадать мажорная версия с .nvmrc
```

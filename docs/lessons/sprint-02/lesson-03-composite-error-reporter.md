# Урок 3 (Sprint 02) — `CompositeErrorReporter` и `ConsoleErrorSink`

Критерий готовности урока выполнен: ошибка уходит во все приёмники; сбой одного (синхронный,
асинхронный, даже сбой самого логирования) не мешает другим и не роняет `report()`.

## Что построили

| Файл | Роль |
|---|---|
| `src/shared/errors/error-event.ts` | Тип `ErrorEvent` (единый вид любой ошибки после нормализации) и функция `toErrorEvent(error, context?)`, которая приводит `AppError`, чужой `Error`, строку или произвольный объект к этому виду. |
| `src/shared/errors/error-event.test.ts` | Тесты нормализации: `AppError`, чужой `Error`, строка, `Object.create(null)`, заморозка события. |
| `src/shared/errors/error-sink.ts` | Второй порт модуля — `ErrorSink { accepts(severity), send(event) }`, контракт одного приёмника. Без реализации и без теста. |
| `src/shared/errors/console-error-sink.ts` | Первая реализация `ErrorSink` — печатает событие в консоль одним вызовом `console.*`, выбранным по `severity`. |
| `src/shared/errors/console-error-sink.test.ts` | Тесты: правильный `console.*` на каждый уровень, `context`/`stack`/`cause` в выводе, `bigint`/циклическая ссылка в `context` не роняют `send()`. |
| `src/shared/errors/composite-error-reporter.ts` | Первая реализация `ErrorReporter` — Композит: рассылает событие по всем `ErrorSink` через `Promise.allSettled`, сбой приёмника логирует напрямую в `console.error`. |
| `src/shared/errors/composite-error-reporter.test.ts` | Тесты критерия готовности: изоляция сбоя (синхронного и асинхронного), фильтрация по `accepts()`, общий объект `event`, устойчивость к сбою самого `console.error`. |
| `src/shared/errors/index.ts` (правка) | Добавлены экспорты `CompositeErrorReporter`, `ConsoleErrorSink`, типов `ErrorEvent`/`ErrorSink`. `toErrorEvent` не экспортируется — внутренняя деталь. |

## Ключевые решения и почему

- **`toErrorEvent` оборачивает всё тело в `try/catch`.** Функция не может быть объявлена как
  «не бросает» — в TypeScript нет такой аннотации: компилятор проверяет форму значений, а не
  то, кинет ли функция исключение по дороге к `return`. Даже `String(error)` может бросить:
  у объекта без прототипа (`Object.create(null)`) нет ни `toString`, ни `valueOf`, и попытка
  привести его к строке падает с `TypeError: Cannot convert object to primitive value`.
  Гарантию «`ErrorReporter` переживает любой мусор на входе» (раздел 15 архитектуры) защищаем
  сами, руками, а не типами.
- **Событие и его `context` заморожены (`Object.freeze`).** Один и тот же объект `event` в
  следующем шаге уйдёт сразу нескольким приёмникам параллельно (`CompositeErrorReporter`) —
  ни один приёмник не должен иметь возможности поменять его для остальных. Тот же приём, что
  `AppError.context` в уроке 2: копия + заморозка, а не заморозка чужого объекта.
- **Мерж контекста: `{ ...context, ...error.context }` — контекст ошибки побеждает.**
  Контекст, переданный в момент вызова `report()` (например, `{ source: 'uncaughtException' }`),
  — это общий фон, известный на месте вызова. Контекст самой ошибки (например, `{ orderId }`)
  задан в точке сбоя и конкретнее. При совпадении ключей побеждает более конкретное.
- **`cause`/`stack` — отдельные поля `ErrorEvent`, а не ключи внутри `context`.**
  `context: Record<string, unknown>` — открытая площадка: ключи придумывает разработчик заново
  в каждом месте, где бросается ошибка, тип не проверяется. `cause` и `stack` — это готовые поля
  самого `Error` в JavaScript (`error.stack`, `error.cause`), они есть у любого `Error` всегда,
  с фиксированным смыслом. Если бы `cause` был просто ключом в `context`, ничто не мешало бы
  где-то в проекте случайно написать `context: { cause: 'клиент не в сети' }` (строка, а не
  объект ошибки!) — и это молча сломало бы любой `ErrorSink`, ожидающий цепочку ошибок.

  **Аналогия 1С.** У документа есть фиксированные реквизиты (Дата, Номер, Ответственный) —
  их смысл и тип заданы конфигурацией. И отдельно — открытая таблица «Дополнительные реквизиты
  и сведения», куда можно дописать любую пару «свойство → значение», не трогая структуру
  документа. `code`/`severity`/`message`/`cause`/`stack` — фиксированные реквизиты `ErrorEvent`;
  `context` — регистр дополнительных сведений.

  **Пример, где разница особенно видна** — обёрнутая ошибка с цепочкой причин:

  ```ts
  try {
    await fetch(url);
  } catch (networkErr) {
    throw new ExternalServiceError('Т-Банк API недоступен', { endpoint: url }, { cause: networkErr });
  }
  ```

  После `toErrorEvent`:

  ```ts
  {
    code: 'EXTERNAL_SERVICE_ERROR',
    severity: 'error',
    message: 'Т-Банк API недоступен',
    context: { endpoint: 'https://sandbox-invest-public-api.tbank.ru/...' },
    cause: TypeError: fetch failed,   // сам по себе целый объект ошибки, со своим message/stack
    stack: 'ExternalServiceError: Т-Банк API недоступен\n    at connectToBroker (...)',
  }
  ```

  `cause` здесь — не строка и не число, а вложенный объект ошибки со своими полями.
  `context: Record<string, unknown>` мог бы технически хранить и его (`unknown` разрешает всё),
  но тогда ничто не подсказывало бы `ConsoleErrorSink`, что этот ключ особый и его, возможно,
  стоит развернуть рекурсивно (напечатать цепочку «эта ошибка ← вызвана этой»). Отдельное поле
  в типе `ErrorEvent` даёт и `tsc`, и приёмнику знание: «здесь всегда либо `undefined`, либо
  ошибка-причина» — без угадывания по ключу.

  Ещё два примера для контраста — простая ошибка без причины и чужой (не `AppError`) `Error`:

  ```ts
  // AppError без cause
  throw new BrokerRejectedError('Заявка отклонена брокером', { orderId: 'A-1042', reason: 'insufficient_funds' });
  // -> { code: 'BROKER_REJECTED', severity: 'error', message: '...', context: { orderId, reason }, cause: undefined, stack: '...' }

  // Чужой Error — баг, а не ожидаемый сбой
  JSON.parse(badJson); // throws SyntaxError
  // -> { code: 'UNKNOWN_ERROR', severity: 'error', message: 'Unexpected token o in JSON...', context: {...}, cause: <сам SyntaxError>, stack: '...' }
  ```

- **`console.*` печатает `event.context` отдельным аргументом, не через `JSON.stringify`.**
  Деньги в проекте — `bigint` (`Money`, урок 6), а `JSON.stringify` бросает `TypeError` на
  `bigint` («Do not know how to serialize a BigInt») и на циклических ссылках («Converting
  circular structure to JSON»). `console.*` печатает объект через `util.inspect` (внутренний
  форматтер Node), который переживает и то, и другое без дополнительного кода с нашей стороны.
- **`CONSOLE_METHOD_BY_SEVERITY` хранит имя метода (`'info'`/`'warn'`/`'error'`), а не саму
  функцию.** Если бы карта хранила `console.info` напрямую (ссылку, взятую в момент загрузки
  модуля), тесты сломались бы: `vi.spyOn(console, 'info')` подменяет метод на объекте `console`
  уже после того, как модуль загружен и ссылка сохранена — старая ссылка так и осталась бы
  указывать на неподменённую функцию. `console[method]` ищет метод заново при каждом вызове
  `send()` — и находит уже подменённый.
- **Стек и `cause` печатаются в том же вызове `console.*`, что и основная строка, а не
  отдельными вызовами после.** Под PM2 несколько процессов пишут в один и тот же поток вывода;
  если бы стек печатался вторым отдельным вызовом, между ним и первым мог бы втиснуться вывод
  совсем другого события из другого процесса.

- **`sinks.map(async (sink) => {...})`, а не `sinks.map((sink) => sink.send(event))`
  напрямую.** `ErrorSink.send` по типу обещает `Promise<void>`, но ничто в рантайме не
  проверяет, что реализация действительно асинхронна — обычная (не `async`) функция может
  бросить синхронно, до того как вернуть хоть какой-то `Promise`. Синхронный `throw` внутри
  колбэка `Array.prototype.map` прерывает саму итерацию: приёмники **после** сломанного вообще
  не получили бы вызов. Обёртка `async (sink) => {...}` ловит и такой `throw`, и `throw` из
  `accepts()`, превращая их в отклонённый `Promise`, который спокойно доедет до
  `Promise.allSettled` вместе с остальными.
- **Сбой приёмника логируется в `console.error` напрямую, а не через `this.report(...)`.**
  Если сломан сам приёмник (а не что-то в приложении), повторный `report()` пройдёт по тем же
  приёмникам и либо зациклится, либо снова тихо упадёт тем же путём. `console.error` —
  независимый нижний уровень, не зависящий от здоровья `sinks`.
- **В сообщении о сбое — имя сломанного приёмника (`sink.constructor.name`), без индексации
  массива.** Первая версия сопоставляла индекс результата `Promise.allSettled` с индексом
  `this.sinks` (`this.sinks[index]`) — рабочий, но хрупкий приём: два параллельных массива,
  которые нужно вручную держать синхронными. `noUncheckedIndexedAccess` (см. отдельный раздел
  ниже) сразу же поймал в этом месте потенциальный `undefined`. Финальная версия просто ловит
  сбой `try/catch`-ем внутри самого колбэка `map` и возвращает пару `{ sink, reason }` —
  приёмник и его сбой едут вместе, без обращения к массиву по индексу вообще.
- **Логирование сбоя обёрнуто в `try/catch` с пустым `catch` — «последний рубеж».**
  `report()` обещает не бросать никогда (раздел 15 архитектуры), а сам `console.error` способен
  бросить — например, `EPIPE`, если под PM2 поток вывода процесса уже закрыт с другой стороны.
  Пустой `catch` обычно признак проглоченной ошибки, про которую забыли, — здесь это осознанный
  выбор: логировать сбой самого логирования уже некуда, мы и так на нижнем уровне отчётности.
  Единственная альтернатива — уронить `report()` целиком, что нарушило бы его главную гарантию.

## `noUncheckedIndexedAccess` в `tsconfig.json`

Перед закрытием урока включили ещё одну проверку `tsc`, которую `strict: true` **не**
включает сама по себе.

**Почему по умолчанию `array[i]` считается «всегда существует».** Тип `T[]` в TypeScript
описывает только то, *что лежит внутри*, если там что-то есть — а не то, сколько элементов в
массиве прямо сейчас. Индекс — это просто `number`, и `array[i]` компилятор типизирует как `T`,
а не `T | undefined`, потому что технически не отслеживает длину массива и границы циклов: это
задача рантайма, не системы типов. `strict: true` включает проверки null/undefined там, где
компилятор **может** статически понять, что значение бывает отсутствующим (необязательные
поля, явный `| undefined` в типе) — но `array[i]` таким явно не размечен, и по умолчанию
TypeScript ему верит на слово.

**Почему это опасно именно у нас.** Не абстрактный риск на будущее — ровно то, что уже
произошло в `composite-error-reporter.ts`: `this.sinks[index]`, где `index` был индексом
**другого** массива (`results`, полученного из `Promise.allSettled`), а не собственно
`this.sinks`. Оба массива в момент написания кода имели одинаковую длину и совпадающий
порядок — но это было неявным допущением, ничем не защищённым, а не гарантией. Малейшее
расхождение (например, если бы `results` где-то отфильтровался) — и `this.sinks[index]` стало
бы `undefined`, при том что тип обещал `ErrorSink`.

Для остального проекта — та же ловушка на данных, которые куда важнее списка приёмников
ошибок: `candles[i + 1]` (следующая по времени свеча) на последнем индексе массива, или
`positions[positions.length - 1]` (последняя открытая позиция) на пустом массиве позиций —
без `noUncheckedIndexedAccess` оба выражения типизируются как «точно есть», хотя в рантайме
дадут `undefined`. Тихий `undefined` там, где ожидается `Money` или `Quantity`, — это ровно
тот класс бага, который в торговом коде обнаруживается не тестом, а падением на реальных
данных.

**Как исправили найденную ошибку — не подавлением, а изменением подхода.** Соблазн — заглушить
ошибку через `this.sinks[index]!` (утверждение «здесь точно есть значение») или `?? someSink`.
Оба варианта возвращают код к состоянию «верим на слово». Вместо этого убрали саму
необходимость сверять два массива по индексу: каждый приёмник теперь сам несёт свой результат
(`{ sink, reason }`), собранный там же, где сбой произошёл (`try/catch` внутри колбэка
`map`), а не восстановленный задним числом через `this.sinks[index]`. Опция не только ловит
баг — она подталкивает к структуре кода, где такого класса бага не может возникнуть вообще.

## Что пошло не так и чему научились

`noUncheckedIndexedAccess: true` в `tsconfig.json` сразу нашёл реальную (пусть и небольшую)
ошибку в `composite-error-reporter.ts` — `this.sinks[index]` там, где `index` брался из другого
массива. Это ровно демонстрация того, зачем опцию включали, а не гипотетический пример.
Остальное на всех трёх шагах прошло без сюрпризов: `typecheck`/`test` — 4 файла теста,
32 теста.

## Вопросы и ответы

**Контрольный вопрос (шаг 1).** Почему `cause` не мог бы жить внутри `context` как обычное
поле, а обязан идти отдельным полем `ErrorEvent`?

> См. раздел «Ключевые решения» выше — краткая суть: `context` открытый и без гарантий по
> ключам, `cause`/`stack` — фиксированные поля с гарантированным смыслом, аналог фиксированных
> реквизитов документа против открытой таблицы дополнительных сведений в 1С.

**Контрольный вопрос (шаг 2).** В тесте на `context` используется `toBe`, а не `toEqual` —
почему именно так, ведь `context` в тесте с циклической ссылкой (`context.self = context`)?

> Разбор `vi`, шпионов/моков и разницы `toBe`/`toEqual`/`toStrictEqual` — отдельной темой,
> не только для этого урока: [`docs/lessons/topics/vitest-mocks.md`](../topics/vitest-mocks.md).

**Контрольный вопрос (шаг 3).** Почему `report()` сам никогда не бросает исключение, даже если
приёмник упал синхронно — и даже если упал сам `console.error`?

> `Promise.allSettled` вместо `Promise.all` — сбой одного приёмника не превращается в
> отклонение всего набора. Обёртка `async (sink) => {...}` ловит и синхронный `throw` внутри
> `send()`/`accepts()`, превращая его в отклонённый результат `allSettled`, а не в исключение,
> прерывающее `map()`. А сам цикл логирования сбоев обёрнут ещё в один `try/catch` — на случай,
> если сломан даже `console.error`. Три независимых рубежа обороны вместо одного — это и есть
> раздел 15 архитектуры: `ErrorReporter` не бросает исключений, потому что любой другой код в
> проекте (`installProcessGuards`, композиция стратегий) вызывает `report()` в расчёте, что это
> безопасно, и не оборачивает его в свой `try/catch`.

## Новые термины (аналогии из 1С)

| Термин | Смысл | Аналогия 1С |
|---|---|---|
| Нормализация на границе | Что угодно снаружи (`unknown`) → один внутренний вид (`ErrorEvent`) | Обработчик, приводящий разные источники ошибки к одной структуре перед записью в журнал |
| Второй порт в модуле | Порты бывают не только «наружу» модуля, но и «внутри», между его же классами | Несколько независимых переопределяемых модулей БСП внутри одной подсистемы |
| Фиксированные поля vs открытый `context` | Гарантированные по типу поля (`cause`, `stack`) против произвольной таблицы «ключ → значение» | Реквизиты документа против «Дополнительных реквизитов и сведений» |
| Адаптер | Конкретная реализация порта под один канал (здесь — консоль) | Драйвер конкретного оборудования под общий интерфейс БПО |
| `vi`, шпион, мок | Служебные инструменты Vitest для подмены/наблюдения за функциями в тестах — см. [отдельную тему](../topics/vitest-mocks.md) | — |
| `toBe` vs `toEqual` | Сравнение по ссылке против сравнения по содержимому — см. [отдельную тему](../topics/vitest-mocks.md) | — |
| Композит | Объект, внутри которого много однотипных, а снаружи — один | Одна запись события → журнал регистрации + письмо администратору (раздел 20, стр. 1191) |
| Переборка (Bulkhead) | Сбой одной части не валит остальные | Ошибка одного регламентного задания не останавливает другие (раздел 20, стр. 1192) — вернётся в уроке 10 (`EventBus`) |
| Разрыв тип/рантайм для `Promise` | Тип `Promise<void>` ничего не гарантирует про то, что функция не бросит синхронно до возврата промиса | — |
| `noUncheckedIndexedAccess` | `array[i]` типизируется как `T \| undefined`, а не `T` — компилятор не верит на слово, что индекс попал в границы | Обращение к строке табличной части по номеру, которого могло не быть — платформа 1С тоже вернула бы `Неопределено`/ошибку, а не притворилась бы, что строка есть |

## Как проверить самому

```bash
npm run typecheck   # tsc --noEmit — 0 ошибок (в т.ч. с noUncheckedIndexedAccess)
npm run test        # vitest run — 4 файла теста, 32 теста зелёных
git status          # error-event.ts(+test), error-sink.ts, console-error-sink.ts(+test),
                     # composite-error-reporter.ts(+test) — новые; index.ts, tsconfig.json — правка
```

Ручная проверка вживую:

```ts
import { CompositeErrorReporter, ConsoleErrorSink } from './src/shared/errors/index.ts';

const reporter = new CompositeErrorReporter([new ConsoleErrorSink()]);
await reporter.report(new Error('тест'));
```

# Урок 2 (Sprint 02) — `AppError` и порт `ErrorReporter`

## Что построили

| Файл | Роль |
|---|---|
| `src/shared/errors/app-error.ts` | Абстрактный базовый класс всех ошибок приложения: `code`, `severity`, `transient`, `context`, `cause`. |
| `src/shared/errors/app-error.test.ts` | Тесты базового поведения через минимальный тестовый подкласс `FakeAppError`. |
| `src/shared/errors/error-reporter.ts` | Порт `ErrorReporter` — единая точка оповещения об ошибке, без реализации. |
| `src/shared/errors/index.ts` | Публичный API модуля `errors/`: `AppError`, `Severity`, `ErrorReporter`. |
| `tsconfig.json` (правка) | Добавлен `verbatimModuleSyntax: true`. |
| `tests/sanity.test.ts` (удалён) | Временный тест выполнил свою роль — заменён настоящим `app-error.test.ts`. |

## Ключевые решения и почему

- **Абстрактный класс, а не интерфейс.** Кроме контракта (`code`/`severity` обязательны)
  есть общая реализация — конструктор, `this.name = new.target.name`. Интерфейс такую
  реализацию разделить между наследниками не позволяет.
- **`context`: копия + заморозка, а не только `Readonly` в типе.** `Readonly<...>` в
  типе — проверка `tsc`, которая исчезает после компиляции; в рантайме объект остаётся
  обычным изменяемым. Поэтому в конструкторе — `Object.freeze({ ...context })`:
  - `{ ...context }` — копия, чтобы мутация объекта, который вызывающий код передал и
    продолжает держать у себя, не протекла в уже созданную ошибку задним числом;
  - `Object.freeze(...)` — чтобы запись в `error.context` уже после создания ошибки
    бросала `TypeError`, а не терялась молча.

  **Как работает `Object.freeze` изнутри.** Это не клонирование и не перемещение в
  памяти. Заморозка меняет **тот же самый** объект: выставляет `[[Extensible]] = false`
  (нельзя добавить новое свойство) и каждому собственному свойству — `writable: false`,
  `configurable: false`. Ссылка (`===`-идентичность) не меняется. Клонирует именно спред
  `{ ...context }` — это отдельная операция, выполняется раньше заморозки. Заморозка ещё
  и **не глубокая**: `Object.freeze({ order: {...} })` защищает только верхний уровень —
  `context.order = {}` бросит `TypeError`, а `context.order.id = 2` пройдёт молча, если
  внутри лежит вложенный объект. Сейчас в `context` кладём только плоские данные (id, коды
  и т.п.), поэтому это не проблема, но граница, о которой нужно помнить.

- **Порядок инициализации: в конструкторе `AppError` нельзя читать `this.code`/`this.severity`.**
  `super(...)` — первое действие конструктора наследника; поля класса наследника
  (`readonly code = '...'`) присваиваются **после** возврата из `super()`. В момент работы
  `AppError`-конструктора их ещё нет.
- **`Object.setPrototypeOf` не нужен.** Это обходной путь для случая, когда `extends`
  встроенного класса (`Error`) компилируется в цель ES5 — там ломается `instanceof`. Наш
  `tsconfig.json` целится в ES2022, `extends` остаётся нативным, `instanceof` работает без
  костылей.
- **Тестируем абстрактный класс через минимальный тестовый подкласс.** `AppError` нельзя
  создать напрямую (`abstract`), поэтому в тесте объявлен `FakeAppError` — самая простая
  реализация контракта, ничего не проверяющая, кроме передачи данных через базовый класс.
- **`ErrorReporter` — только интерфейс, без теста.** У чистого контракта нет поведения,
  которое можно проверить в рантайме; поведение появится вместе с первой реализацией
  (`CompositeErrorReporter`, урок 3) — тестировать будем её.
- **`verbatimModuleSyntax: true` в `tsconfig.json`.** `tsc` проверяет типы по всему проекту
  и сам знает, что `ErrorReporter`/`Severity` — типы, а не значения. Но `tsx` и `vitest`
  транспилируют/исполняют файлы **по отдельности** через `esbuild`, который типов не читает
  вообще, только синтаксис. Реэкспорт `export { ErrorReporter } from '...'` без слова `type`
  esbuild трактует как реэкспорт значения; в рантайме такого значения нет (интерфейсы
  стираются при компиляции) — при запуске это упало бы с «does not provide an export
  named…», хотя `npm run typecheck` был бы зелёным. `verbatimModuleSyntax` требует писать
  `export type`/`import type` явно везде, где экспортируется только тип, — и превращает эту
  категорию ошибок в ошибку `tsc`, а не в сюрприз на исполнении. Поэтому в `index.ts`:
  `export { AppError }` (класс, значение), но `export type { Severity }` и
  `export type { ErrorReporter }` (только типы).
- **`tests/sanity.test.ts` удалён.** Его роль (доказать, что `vitest` находит тесты) выполнил
  настоящий `app-error.test.ts`. Каталог `tests/` временно пуст — заполнится в уроке 8
  (`FakeClock` и другие общие фейки, раздел 4 структуры архитектуры); git пустые папки не
  отслеживает, это ожидаемо.

## Что пошло не так и чему научились

Ничего непредвиденного: обе проверки (`typecheck`, `test`) прошли с первого раза на каждом
шаге. Число тестов в выводе `vitest` закономерно упало с 9 (шаг 1, вместе с `sanity.test.ts`)
до 8 (шаг 2, после его удаления) — не потеря теста, а ожидаемый результат уборки.

## Вопросы и ответы

**Контрольный вопрос.** В тесте «`context` — копия» мы меняем `source.orderId` и добавляем
`source.extra` уже после создания `error`. Что именно этот тест проверяет — что `context`
заморожен или что это копия? Подсказка: заморозь `source`, а не `error.context`, и подумай,
что тогда сломается.

> Тест «копия» проверяет **только** факт, что `error.context` — отдельный объект, а не та
> же ссылка, что `source` (изменения снаружи не протекают внутрь). Заморозку он не
> проверяет вовсе: если бы конструктор замораживал сам переданный объект без спреда
> (`Object.freeze(context)`), `error.context` и `source` указывали бы на один и тот же
> объект, и строка `source.orderId = '2'` бросила бы `TypeError` **до** `expect` — тест бы
> упал по другой причине, а не подтвердил копирование.
>
> Если заранее заморозить `source` (`Object.freeze(source)`) перед передачей в конструктор —
> в тесте ничего не меняется: `{ ...context }` одинаково клонирует что замороженный, что
> обычный объект-источник. Это показывает, что тест «копия» и тест «заморожен» проверяют
> **два независимых факта**: (1) `error.context !== source` и (2) `error.context` нельзя
> изменить напрямую после создания ошибки. Можно было бы сделать одно без другого — у нас
> сделаны оба.

## Новые термины (аналогии из 1С)

| Термин | Смысл | Аналогия 1С |
|---|---|---|
| Абстрактный класс | Контракт + общая реализация; создать экземпляр напрямую нельзя | Базовая (родительская) конфигурация с обязательными к переопределению процедурами |
| `Object.freeze` | Блокирует запись в объект **на месте**, без копирования; заморозка не глубокая | Пометка «Только просмотр» на уже существующем объекте, а не создание его копии |
| `new.target` | Внутри конструктора — ссылка на реальный вызванный класс-наследник | Определение конкретного вида документа изнутри общей процедуры проведения |
| `Error.cause` | Стандартное поле JS для цепочки «что к чему привело» | Ссылка на документ-основание |
| Порт (интерфейс) без реализации | Контракт объявлен, реализации ещё нет — появится позже | Переопределяемый модуль БСП с процедурой-затычкой, которую ещё не заполнили |
| `verbatimModuleSyntax` | Требует явного `export type`/`import type` для типов, иначе однофайловый транспилятор (esbuild) может сгенерировать нерабочий реэкспорт | Явное указание, что реквизит — вычисляемый (не хранимый), чтобы платформа не пыталась читать его как обычное поле |

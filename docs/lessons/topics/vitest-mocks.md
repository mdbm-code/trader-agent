# Vitest: `vi`, шпионы, моки и `toBe` vs `toEqual`

Сквозная тема, не привязанная к одному уроку — ссылаются другие конспекты, когда встречают
`vi.spyOn`/`vi.fn`/`toBe` впервые в контексте.

## `vi`

`vi` — служебный объект Vitest для работы с подделками: создание, подмена, восстановление.
Аналог `jest` из Jest, если попадались статьи или примеры на нём. Импортируется как обычное
значение: `import { vi } from 'vitest'`.

## Шпион (spy)

Обёртка вокруг функции, которая **запоминает вызовы**: сколько раз её вызвали и с какими
аргументами. По умолчанию шпион не меняет поведение — вызывает настоящую функцию, как будто
слежки и нет, только ведёт запись.

`vi.spyOn(obj, 'метод')` подменяет **метод существующего объекта** — например, `console.error` —
на такую записывающую обёртку.

## Мок (mock)

Подмена **поведения** функции: вместо настоящей работы она делает то, что задано в тесте.

- `vi.fn()` создаёт **новую** подставную функцию с нуля — когда нет существующего объекта/метода,
  который нужно подменить, а просто нужна функция-заглушка (например, колбэк, который передают
  куда-то и потом проверяют, был ли он вызван).
- `vi.spyOn(obj, 'метод').mockImplementation(fn)` — шпион **и** подмена поведения сразу: метод
  существующего объекта заменяется на `fn`, вызовы по-прежнему записываются.
- `.mockImplementation(() => {})` делает шпиона «немым»: вызовы записываются, но в консоль
  ничего не выводится (или что угодно ещё) — то, что используется в тестах `ConsoleErrorSink` и
  `CompositeErrorReporter`, чтобы вывод `npm test` не заваливало реальными строками лога.

## `spy.mock.calls`

У любого шпиона/мока есть `.mock.calls` — массив массивов: один внешний элемент на каждый
вызов, внутри — аргументы этого вызова по порядку.

```ts
console.error('[ERROR] X: y', { a: 1 });

spy.mock.calls[0]      // ['[ERROR] X: y', { a: 1 }] — аргументы первого вызова
spy.mock.calls[0][0]   // '[ERROR] X: y'              — первый аргумент первого вызова
spy.mock.calls[0][1]   // { a: 1 }                    — второй аргумент первого вызова
```

`expect(spy).toHaveBeenCalledTimes(n)` и `expect(spy).toHaveBeenCalledWith(...)` — готовые
проверки поверх того же `.mock.calls`, для частых случаев.

## `vi.restoreAllMocks()`

Возвращает настоящие функции на место. Без него подмена «утечёт» в соседние тесты: `vi.spyOn`
физически меняет свойство на объекте (`console` — общий, один на весь тестовый файл), и если не
вернуть его после теста, следующий тест унаследует уже подменённый метод — его вызовы попадут в
старый мок, а не в новый, поставленный внутри него самого, и счётчики вроде `toHaveBeenCalledTimes`
начнут врать. Вызывается в `afterEach`, чтобы это происходило автоматически после каждого теста.

## `toBe` vs `toEqual` / `toStrictEqual`

Все три — способы сравнить «то, что получилось» с «тем, что ожидали», но проверяют разное.

- **`toBe(x)`** — по сути `Object.is(actual, x)`. Для примитивов (числа, строки, `boolean`) это
  обычное сравнение значения. Для объектов и массивов — **сравнение по ссылке**: истина, только
  если слева и справа буквально один и тот же объект в памяти, а не просто похожий по форме.
  Никакого обхода содержимого не происходит вообще.
- **`toEqual(x)`** — **глубокое структурное сравнение**: рекурсивно обходит собственные поля
  и сравнивает значения. Два *разных* объекта с одинаковым содержимым считаются равными.
  Не различает `{ a: undefined }` и `{}` (оба «нет значащего `a`»).
- **`toStrictEqual(x)`** — тоже глубокое сравнение, но строже: `{ a: undefined }` и `{}` уже
  **не** равны, и экземпляр класса не равен обычному объекту с теми же полями (`instanceof`
  учитывается). Выбирают, когда важно не спутать «поле есть и оно `undefined`» с «поля нет»,
  или не спутать «настоящий объект нужного класса» с «объект такой же формы».

**Когда что выбирать.** Если тест проверяет содержимое результата (например, вернула ли функция
объект с нужными полями) — `toEqual`/`toStrictEqual`. Если тест проверяет, что **это тот же
самый экземпляр**, а не пересозданная копия — только `toBe`.

### Почему в тесте «один и тот же `event` доходит до всех приёмников» нужен именно `toBe`

Тест устроен так:

```ts
const first = new NormalSink();
const second = new NormalSink();
const reporter = new CompositeErrorReporter([first, second]);

await reporter.report(fakeError());

expect(first.sent[0]).toBe(second.sent[0]);
```

Смысл теста — доказать конкретное архитектурное свойство: `CompositeErrorReporter` вызывает
`toErrorEvent` **один раз** и передаёт **одну и ту же ссылку** во все принимающие приёмники, а
не создаёт отдельное событие (или копию) под каждый `sink`.

Если бы код по ошибке раздавал каждому приёмнику свою копию, например:

```ts
this.sinks.map((sink) => sink.send({ ...event }))
```

— `first.sent[0]` и `second.sent[0]` были бы двумя **разными** объектами с одинаковым
содержимым. `expect(first.sent[0]).toEqual(second.sent[0])` в этом случае **всё равно прошёл
бы**: глубокое сравнение не отличает копию от оригинала, если поля совпадают. Тест остался бы
зелёным, хотя код уже не делает того, что было задумано — например, если бы позже понадобилось,
чтобы один приёмник мог как-то пометить событие и второй это увидел (гипотетически), с копиями
это перестало бы работать, а тест на `toEqual` ничего бы не заметил.

`expect(first.sent[0]).toBe(second.sent[0])` — сравнение по ссылке — на этом сценарии **упал
бы**, потому что `{ ...event }` создаёт новый объект в памяти. Именно поэтому только `toBe`
действительно проверяет заявленное свойство «тот же объект»: `toEqual` тут дал бы ложное чувство
защищённости, пропустив ошибку, которую тест как раз должен ловить.

# Стандарт: задачи, попытки, проверки

Задания раздаются **файлами**, а не сообщениями в чате. Короткая команда
пользователя (`P001-T003`) лишь находит работу и запускает подробный протокол.
Право записи даёт **подтверждение владельца** для конкретной сессии.
Прямое однозначное поручение в этом чате может уже содержать это подтверждение
(START, разделы 3 и 5); официальный файл задачи и назначение всё равно обязательны.

---

## 1. Коды

| Код | Что это | Пример |
|---|---|---|
| `Pnnn` | постоянный код проекта (области работ) из `_meta/workspace.yaml` | `P001` |
| `Tnnn` | номер задачи внутри проекта, по порядку, не переиспользуется | `T003` |
| `Pnnn-Tnnn` | полный идентификатор задачи | `P001-T003` |
| `A0N` | попытка выполнения (attempt) | `A01`, `A02` |
| `R0N` | проверка ревьюером (review) | `R01` |

В обращении к владельцу обозначай «проект P001», «задача P001-T003»,
«чат …». Код задачи не является идентификатором чата: одну задачу могут
последовательно выполнять разные чаты.

## 2. Где лежит задача

```
<папка проекта>\docs\tasks\
  README.md            список задач проекта (ведёт оркестратор)
  T003\
    TASK.md            поручение, официальные статусы, назначения, сдачи — пишет ТОЛЬКО оркестратор
    A01.md             отчёт исполнителя попытки 1 — пишет ТОЛЬКО он
    A02.md             попытка 2 (если продолжил другой исполнитель)
    R01.md             отчёт ревьюера — пишет ТОЛЬКО этот ревьюер
```

Для P000 — `_meta\docs\tasks\`. Шаблоны — `_meta\templates\task\`.

**Правило владения файлами:** каждый пишет только свой файл. Новый исполнитель
не дописывает в чужой `A01.md` даже пометку «прервана» — прекращение фиксирует
оркестратор в `TASK.md`.

**Свой отчёт можно писать всегда.** Исполнитель вправе менять свой `A0N.md`,
ревьюер — свой `R0N.md`, даже если в задаче перечислены только другие файлы.

## 3. Статус задачи (в `TASK.md`, меняет только оркестратор)

```
draft ──► ready ──► in_progress ──► review ──► done
                       ▲   │  ▲        │
                       │   ▼  └────────┘  возврат на доработку
                     blocked
                                    cancelled — из любого состояния
```

| Статус | Значение |
|---|---|
| `draft` | черновик, не готова к выполнению |
| `ready` | подготовлена к назначению (**не** «бери, кто хочет») |
| `in_progress` | есть выданное или активное назначение; у координационной задачи записаны ведущий и поручение начать работу |
| `review` | результат сдан и записан в «Сдачи», идёт проверка и приёмка |
| `done` | принятый владельцем коммит интегрирован, как требует задача |
| `blocked` | работа остановлена до решения вопроса (причина записывается) |
| `cancelled` | задача отменена |

**Переходы, которые нужно делать явно:**

- `review → in_progress` — **возврат на доработку**: оркестратор записывает причину
  (ссылка на `R0N.md` или решение владельца), сдачу помечает `отклонена`, решает:
  продолжает ли та же сессия (назначение снова `активна`) или выдаётся новая попытка.
- `blocked → in_progress` — после решения вопроса, с записью, что решено.
- Изменение цели, границ или критериев — **новая редакция** задания (раздел 6).

### 3.1. Координационная задача

Координационная задача объединяет испытания, наблюдения или принятие связанных
результатов; её ведёт оркестратор без отдельного исполнителя. В карточке укажи
`task_type: coordination`, ведущую подтверждённую сессию, поручение владельца,
план и место записи результатов. Отсутствующее поле `task_type` означает обычную
задачу `implementation`. Тип определяется содержанием, а не удобством обхода приёмки.

- `ready`: план и критерии подготовлены; поручения начать ещё нет.
- `in_progress`: владелец поручил начать, ведущий записан, собираются результаты.
- `review`: все результаты и ограничения записаны, в «Сдачах» зафиксирован
  полный SHA и путь к результату; вместо номера попытки указано «оркестратор».
- `done`: владелец принял этот SHA, результат находится в main, итог записан.

Не создавай фиктивную попытку A01 для учёта координации. Дочерние задачи имеют
свои назначения и приёмку; состояние родительской определяется её критериями.
Провал сценария разбирается в результатах; критерии не ослабляются ради закрытия.
Возврат из review и остановка в blocked фиксируются с причиной по общему порядку.

Если весь результат — разрешённый учёт, его можно записывать в main по ходу
работы. Предъявляется конкретная ревизия main; ранняя запись учёта не означает
приёмки. При принятии SHA, уже входящего в main, повторное слияние не нужно:
проверь наличие коммита и неизменность результата, запиши принятый SHA и отдельный
учётный коммит закрытия. Изменение самого результата после сдачи требует новой
сдачи и согласования. Изменения правил или реализации по-прежнему готовятся
в рабочей ветке и принимаются до интеграции.

## 4. Назначения (таблица в `TASK.md`, меняет только оркестратор)

| Статус назначения | Значение |
|---|---|
| `выдана` | оркестратор создал назначение; сессия исполнителя ещё не подтверждена |
| `активна` | владелец подтвердил конкретную сессию (её данные записаны) |
| `сдана` | результат зафиксирован в «Сдачах» с полным SHA |
| `прекращена` | остановлена: обрыв чата, передача другому, отмена |
| `принята` / `отклонена` | итог приёмки этой сдачи |

**Новая независимая сессия = новая попытка** (по назначению оркестратора).
Простое возобновление той же сессии новую попытку не требует.
Открытие второго чата **не отменяет** полномочий первого: передача оформляется
явно — старое назначение `прекращена`, новое `выдана`.
Это относится к той же попытке или проверке. Разные задачи с отдельными
назначениями могут выполняться одновременно. Для оркестраторов граница
исключительности — проект; их сессии учитываются в `docs/STATE.md` своих проектов.

### Связь назначения с сессией

1. Оркестратор создаёт назначение со статусом `выдана`.
2. Владелец поручает задачу в новом или уже открытом чате; короткая форма — код задачи.
3. Агент пишет квитанцию входа. Если прямое поручение ещё не подтверждает
   однозначно эту сессию и назначение, **просит подтвердить** именно недостающую часть.
4. Получив подтверждение либо установив его наличие в этом чате по START,
   раздел 5, агент записывает источник подтверждения и данные сессии
   в свой `A0N.md` и делает первый коммит в назначенную ветку.
5. Оркестратор при следующем обращении переносит данные сессии в таблицу
   назначений и ставит `активна` (это ведение учёта).

Если в назначенной ветке уже есть `A0N.md` с подтверждённой другой сессией,
а назначение не прекращено — новый чат **останавливается** и сообщает владельцу.

### 4.1. Временная оркестрация

Временная работа оркестратора фиксируется в официальной задаче с целью,
разрешёнными путями и действиями, подтверждённой сессией и проверяемым условием
завершения. Состояние полномочий ведётся отдельно от статуса задачи и назначения
A0N/R0N по [правилам роли](../roles/project-orchestrator.md#временные-поручения).
Это может быть ограниченное поручение P000, включая ведение учёта и интеграцию
после приёмки; оно не назначает постоянного координатора всех проектов.

Оркестратор сохраняет управление всеми исполнителями и ревьюерами, назначенными
на задачи его области. Координация нескольких самостоятельных проектов требует
отдельного поручения с перечислением проектов и действий. Приёмка локальных
результатов остаётся в их проектах, если владелец явно не поручил другой порядок.

После выполнения условия оркестратор записывает завершение дополнительных
полномочий. Если остались работающие агенты или непринятые результаты, он
фиксирует их состояние и согласованный порядок продолжения; фактический статус
задачи сохраняется. Преемник требуется для передаваемой незавершённой работы,
а для законченного поручения не требуется. Входящая заявка другой сессии сама
по себе не продлевает и не расширяет поручение.

## 5. Сдача результата и её фиксация

1. Исполнитель делает последний коммит, в котором его `A0N.md` имеет
   **состояние отчёта «готов к проверке»**. Этот коммит и есть предъявляемый результат.
   Свой собственный SHA в этот же файл исполнитель не вписывает (это невозможно).
2. Оркестратор находит этот коммит, проверяет состояние отчёта
   (`git show <SHA>:docs/tasks/T003/A01.md`) и **до начала ревью** записывает
   в таблицу «Сдачи» `TASK.md`: попытку, **полный SHA**, путь отчёта, дату.
   Назначение получает статус `сдана`, задача — `review`. Если у проекта есть
   зарегистрированная удалённая копия, оркестратор отправляет туда `main` и ветку
   сдачи ([GIT, раздел 14](GIT.md#14-удалённая-копия-и-отправка-push)).
3. Дальнейшие коммиты в ветку исполнителя **не меняют** зафиксированную сдачу.
   Новый результат — новая строка в «Сдачах».
4. Ревьюер проверяет **именно записанный SHA** (см. [roles/reviewer.md](../roles/reviewer.md)).
5. Владелец подтверждает **этот SHA**; интегрируется он же (см. [GIT.md](GIT.md), раздел «Интеграция»).

Различаются: коммит реализации, отчёт о ней и окончательно предъявленная ревизия.

Запрос приёмки указывает проект, задачу, точное имя чата оркестратора для ответа,
полный SHA, что изменено, что проверено, ограничения и что произойдёт после принятия.
Если имя текущего чата клиент не показывает, напиши «этот текущий чат Codex/Claude»
и не выдумывай название. Дай готовую фразу, например:

> В этом чате оркестратора ответь: «Принимаю задачу P001-T003 проекта P001,
> коммит <полный SHA>». После принятия результат будет интегрирован, задача закрыта.

«Принял» без SHA или сообщение агента о принятии в другом чате недостаточны:
уточни решение здесь. Короткий SHA допустим, если он однозначно разрешается
в записанный полный SHA и прямо указан в решении владельца. Прямое разрешение
владельца, доступное оркестратору из другого чата, допустимо только при проверяемом
источнике и точном соответствии задачи и SHA; пересказ без такого источника
не заменяет подтверждения. После изменения результата предъяви новый SHA.

## 6. Редакции задания

У `TASK.md` есть поле `revision`. Любое изменение цели, границ или критериев
приёмки — новая редакция с записью в разделе «История редакций».
Попытка и проверка всегда ссылаются на редакцию, по которой работали.

**Исполнитель не вправе ослаблять критерии приёмки**, чтобы объявить задачу выполненной.

## 7. Что обязательно в задаче

В задаче изменения оргполитики в разрешённую область обязательно включаются
`VERSION` и `CHANGELOG.md`; указываются исходная версия, кандидат нового номера,
уровень и критерий их совместной сдачи с правилами. Автор обосновывает уровень
по [POLICY_VERSIONING.md](POLICY_VERSIONING.md); отсутствие этих частей блокирует
сдачу и приёмку. При старом назначении с неполной областью P000 сначала
оформляет уточнение задания. Задачам реализации компонентов повышение версии
оргполитики не требуется.

- цель (зачем, а не только что);
- контекст — с чего начать чтение;
- что можно менять и что нельзя (свой отчёт разрешён всегда);
- зависимости от других задач и проектов;
- проверяемые критерии приёмки;
- как проверить;
- исходная ревизия (полный SHA) и целевая ветка.

Хорошо: «Навык должен вызываться из тестового приложения без запуска ассистента.
Приёмка — тест успешного перевода и тест недоступного провайдера.»
Плохо: «Сделать перевод правильно, следуя всем стандартам.»

## 8. Делегирование подготовки общих документов

Оркестратор может **поручить исполнителю подготовить изменение** файлов, которые
обычно пишет сам (глоссарий, стандарты, роли, шаблоны), — только в конкретной
задаче, где эти файлы явно перечислены в «Что можно менять». При этом:

- работа идёт в отдельной рабочей копии (для `_meta` — всегда, см. [START.md](../START.md));
- подготовленная редакция — **объект работы**, а не действующие правила
  и не новые полномочия исполнителя;
- исполнитель не меняет критерии приёмки своей задачи и правила, по которым
  проверяется его собственная работа;
- ответственность за приёмку остаётся у оркестратора и владельца.

## 9. Номер задачи и запуск

Оркестратор, выдав назначение, передаёт владельцу одну инструкцию запуска:

| Поле | Что указать |
|---|---|
| Проект и задача | Код и понятная цель: какой результат получим |
| Чат | Точное предлагаемое имя, например `P001-T003 A01`; дальше использовать его |
| Клиент | Claude Code, Codex или другой согласованный клиент |
| Папка запуска | Абсолютный путь; назначенная рабочая копия указана отдельно |
| Модель и усилие | Рекомендация и причина по проверенным доступным сведениям |
| Первое сообщение | Точная команда `P001-T003` или `Ревью P001-T003` |
| Действие владельца | Подтвердить сессию, если прямое назначение ещё не дано; затем дождаться результата |

**Оркестратор открывает чат сам**, если его клиент это умеет и владелец в чате оркестратора
прямо решил назначить попытку или проверку. Тогда инструкция владельцу не нужна: поля таблицы
выше оркестратор применяет сам и записывает в назначение решение владельца, имя и идентификатор
сессии и папку (START, раздел 5). Владелец лишь открывает новый чат, если хочет посмотреть работу.

Для уже открытого чата укажи связь новой карточки с прежним прямым поручением
владельца. Повтор команды только ради присвоенного номера не нужен, если работа,
сессия и назначение совпадают. Сообщение оркестратора не заменяет поручение владельца.

Название модели рекомендуй, только если её наличие в выбранном клиенте
подтверждено текущими сведениями. Для другого клиента или неизвестного списка
напиши «выбери сам из доступных; предпочтительна модель для <характера задачи>».
Усилие указывай, если клиент предлагает такой параметр; иначе «если доступно»
или «не применимо». Зафиксируй фактический выбор в данных сессии, когда он станет
известен. Не приписывай клиенту чужую линейку и не угадывай скрытые параметры.
Список моделей не закрепляй как вечное правило; справочные сведения датируются.

Файл задачи **сам не запускает** агента. Автоматического диспетчера нет.

Испытания остановки готовятся заранее по
[пояснению об экзамене](../explanations/process-exam.md). Разбор плана
и смоделированная остановка не называются проверкой реального сбоя клиента.

## 10. Заявки в другой проект

Оркестратор не пишет в каталог задач чужого проекта. Нужна работа в другом
проекте → он создаёт в **своём** проекте задачу-заявку (`draft`, в названии
«Заявка в Pnnn») и сообщает владельцу. Оркестратор целевого проекта, получив
поручение владельца, заводит собственную задачу со ссылкой на заявку.

Ожидание заявки ограничивает только зависимую работу. Оно не требует завершить
сессию оркестратора целевого проекта или остановить остальные задачи своего.
Общие файлы и ресурсы меняются через ответственный проект в согласованной области.

**Первичная регистрация** ещё не существующего в реестре проекта — исключение
из требования иметь задачу-заявку в нём. Прямого поручения владельца достаточно,
чтобы P000 оформил свою задачу регистрации по COMPONENTS, раздел 7. Документация
и реализация нового проекта не входят в неё автоматически.

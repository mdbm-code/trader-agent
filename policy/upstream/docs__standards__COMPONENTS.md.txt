# Стандарт: компоненты

**Компонент** — самостоятельная часть экосистемы со своей ответственностью,
публичным интерфейсом, тестами и документацией. Одна папка в корне рабочего
пространства = один проект = один Git-репозиторий = один ответственный оркестратор.

**Одна активная сессия оркестратора на проект.** Оркестраторы разных проектов
работают параллельно и ведут `docs/STATE.md` каждый в своём репозитории.
P000 отвечает за общие документы; его активность не занимает роль в других проектах.

Отдельный репозиторий создаётся для самостоятельного компонента или области
ответственности, а **не** для каждой технической подпапки.

---

## 1. Три независимые характеристики

Не путать **что** компонент делает, **как** он поставляется и **через что**
к нему обращаются:

| Характеристика | Вопрос | Примеры значений |
|---|---|---|
| **Вид** (`kind`) | За что отвечает? | app, channel, skill, connector, service, library, lab, meta |
| **Поставка** (`runtime`) | Как исполняется? | python-package, node-package, container, host-process, external-api |
| **Интерфейсы** (`interfaces`) | Как к нему обращаться? | package, http, mcp-stdio, mcp-http, cli |

Например, почтовый коннектор: вид — connector, поставка — container,
интерфейсы — mcp-http. Навык перевода: вид — skill, поставка — python-package,
интерфейс — package.

## 2. Виды и префиксы папок

| Вид | Префикс | За что отвечает |
|---|---|---|
| app | `app-` | собственный пользовательский сценарий, настройки, состояние, правила |
| channel | `ch-` | приём событий и показ результата: Telegram, веб, голос, VR |
| skill | `sk-` | законченный переиспользуемый сценарий (часто многошаговый) |
| connector | `conn-` | работа с внешней системой: почта, 1С, Windows-хост |
| service | `svc-` | вычисления: перевод, генерация, распознавание, синтез |
| library | `lib-` | общие контракты и технический код, без своего процесса |
| lab | `lab` | эксперименты и обучение; в приложения не попадает |
| meta | `_meta` | организация экосистемы (только P000) |

**Как выбрать вид — вопросы по порядку, первый «да» решает:**

1. Это способ, которым человек общается с системой? → `ch-`
2. Это работа с конкретной внешней системой? → `conn-`
3. Это тяжёлое вычисление или модель? → `svc-`
4. Это законченный сценарий, который нужен разным приложениям? → `sk-`
5. Это собственный продукт со своими пользователями и правилами? → `app-`
6. Ничего из этого, общий технический код? → `lib-`
7. Проба и учёба? → `lab`

Несколько родственных функций живут в одном компоненте: чтение, поиск и
отправка почты — один `conn-mail`, а не три папки.

## 3. Паспорт `unit.yaml`

Это **наш собственный формат** — описание компонента для людей и проверяющих
скриптов. Он ничего не запускает.

```yaml
schema_version: 1
id: sk-translate          # = имя папки
code: P006                # код из workspace.yaml
kind: skill
version: 0.1.0
runtime: python-package
interfaces: [package]

provides:                 # какие возможности (контракты) предоставляет
  - text.translate.v1
requires:                 # какие возможности нужны от других
  - translation.engine.v1

owner_role: "оркестратор P006"
```

## 4. Что лежит в папке компонента

Обязательно — для всех компонентов (исключение: `_meta` — это не компонент,
а организация экосистемы; паспорт `unit.yaml` ей не нужен, её описывает
запись P000 в `workspace.yaml`):

| Файл | Зачем |
|---|---|
| `AGENTS.md` | вход для агентов: связь с правилами экосистемы и локальные особенности |
| `CLAUDE.md` | одна строка `@AGENTS.md` (адаптер для Claude Code) |
| `README.md` | для человека: что это, как запустить, как проверить |
| `unit.yaml` | паспорт |
| `.gitignore` | создаётся **до первого `git add`** |
| `docs/STATE.md`, `docs/JOURNAL.md`, `docs/tasks/` | учёт работы |

По применимости:

| Файл | Когда |
|---|---|
| `Dockerfile`, `compose.yml` | компонент запускается контейнером |
| `.env.example` | нужны настройки или секреты (только фиктивные значения) |
| `tests/` | есть код |
| `docs/adr/`, `docs/explanations/` | есть локальные архитектурные решения и пояснения |

Шаблон — `_meta/templates/component/`. Файл `gitignore.template` из шаблона
копируется в компонент под именем `.gitignore` (в шаблоне он назван иначе,
чтобы не действовать на сам репозиторий `_meta`).

## 5. Зависимости между компонентами

> **Компоненты не обращаются к внутренностям друг друга.
> Публичные пакеты и документированные интерфейсы разрешены.**

Нормально: `app-assistant` устанавливает пакет `sk-translate`;
`sk-translate` вызывает публичный API `svc-hy-mt`.

Ненормально: навык импортирует внутренние классы приложения; навык требует
весь `AssistantState`; приложение читает файлы или таблицы, которыми владеет другое.

**Фиксация версий:**

| Ситуация | Как подключать |
|---|---|
| совместная разработка | явно выбранная рабочая копия, например `pip install -e ..\sk-translate` |
| приёмка и воспроизводимая сборка | **полный идентификатор коммита** (тег можно переназначить) |
| внешний репозиторий в сборке | фиксированный коммит или образ по digest, не плавающая ветка |

## 6. Сборки

- У компонента-контейнера свой `compose.yml`.
- Совместные сборки — в `_meta/compose.<имя>.yml`, подключают компоненты через
  `include` и имеют явное имя проекта (`name: eco-<имя>`).
- Тяжёлые общие сервисы — `_meta/compose.shared.yml` и общая внешняя сеть.
- Профили (`profiles`) — для необязательных сервисов. Профиль `gpu` выбирает,
  **что** запускать, но не решает, поместится ли всё в видеопамять.

## 7. Регистрация и запуск проекта

Регистрация в реестре и подготовка самого проекта — отдельные результаты.
Незавершённая работа другого проекта не является их зависимостью.

### Короткая регистрация в P000

1. Владелец поручает зарегистрировать проект: понятны назначение, имя папки,
   репозиторий (существующий адрес или явно `local`) и будущий ответственный
   оркестратор, если уже назначен. До регистрации можно читать и готовить
   предложения в чате; полномочий писать в чужой проект это не даёт.
2. Оркестратор P000 проверяет `workspace.yaml` и историю резервов кодов
   в своих официальных задачах `main`. Выбирает следующий ещё не использованный
   код, фиксирует резерв `Pnnn → папка → репозиторий` в задаче регистрации
   и коммитит учёт **до выдачи следующего кода**. Отменённые резервы не переиспользуются.
3. В отдельной рабочей копии P000 готовится только согласованная регистрация:
   код, уникальная папка, репозиторий, вид, краткое описание, статус `planned`.
   Два запроса получают разные коды, даже если первый ещё не принят в реестр.
4. Владелец принимает конкретный SHA; P000 интегрирует его. После этого запись
   в `workspace.yaml` официальна. Статус `planned` не утверждает, что папка,
   документация или работающая версия уже существуют.

Учётный резерв не разрешает менять реестр в основной папке без приёмки.
Код, уже занятый в реестре или резерве, не выдаётся повторно. Перед интеграцией
P000 сверяет реестр и резервы заново; конфликт разрешается с новой сдачей,
как требует GIT, раздел 5.

### Подготовка проекта его назначенным оркестратором

Если репозиторий и минимальный учёт уже существуют, назначенный владельцем
оркестратор входит по своей роли, регистрирует сессию **в своём проекте** и
организует дальнейшие задачи. Прямое назначение по имени проекта связывается
с полученным кодом без повторной передачи роли P000.

Если ещё нет репозитория, `main` или обязательных входных документов, нельзя
молча считать их готовыми. Нужна **отдельная задача запуска в P000** по поручению
владельца: пока своего учёта нет, она хранит границы создания, будущую папку,
код проекта, подтверждённую сессию и место подготовки. Это устраняет круговое
требование создать задачу внутри ещё не созданного проекта.

Назначенному оркестратору будущего проекта можно выдать попытку подготовки
по этой задаче в отдельной копии P000. В ней он готовит комплект
`templates/component/` с локальными уточнениями, `.gitignore` и документацией,
предъявляет SHA владельцу; это **не передаёт ему роль оркестратора P000**.
Задача явно определяет, кто и куда переносит принятый комплект, создаёт
репозиторий и его первый коммит, как проверяет совпадение дерева файлов и
фиксирует оба SHA. Такие действия не разрешаются одной записью `planned`.

**Перенос можно поручить оркестратору самого нового проекта.** Хранение задачи
запуска в P000 не назначает P000 исполнителем переноса автоматически. Задача
указывает подтверждённую сессию, точный принятый SHA и исходный `component/`,
целевой путь и репозиторий, проверку его исходного состояния, первый коммит
и сверку Git-дерева. Если целевой репозиторий уже содержит другую работу,
исполнитель сохраняет её и согласует порядок переноса с владельцем.

Исполнитель записывает результат в свой отчёт и учёт нового проекта; учёт
официальной задачи P000 обновляет её ответственный оркестратор. Для такого
обновления достаточно ограниченного поручения P000 по
[TASKS, раздел 4.1](TASKS.md#41-временная-оркестрация). Подготовка или перенос
сами по себе не передают исполнителю общее управление P000. Смена ранее
указанного исполнителя или порядка переноса требует решения владельца и
фиксации новой редакции задания, а не молчаливой смены роли.

После приёмки комплекта и появления основной папки на `main` оркестратор
регистрирует сессию в `<проект>/docs/STATE.md`, ссылаясь на исходное назначение
владельца; задачи реализации ведутся уже в проекте. При подготовке собственного
результата оркестратор пишет отдельный отчёт и не называет его независимым ревью.
Принимает конкретный SHA владелец. P000 не ждёт завершения реализации, чтобы
регистрировать следующие проекты или вести другие независимые задачи.

# Маршрут первого релиза федерации после M1

Дата: 31.10.2026, Europe/Moscow. Статус: **документационный черновик для просмотра
Архитектором FCIA**. Постановка ARCH-CORE-PLAN-DOC-20261031-01. M2, последующие

## Актуальный маршрут — 01.11.2026

Действующее решение владельца — [Linux-first](https://github.com/mdbm-code/ai-ecosystem-core/issues/6#issuecomment-6564170437): первый пилот на **двух отдельных Linux-узлах** с принятым точным Core, постоянными installation/domain/journal/project/task IDs, настоящим owner-admitted компонентом и Naming **L/R/C/D на реальном согласованном GitHub repo**. Обязательны двусторонний каталог с происхождением/ACK, работа компонента, обновление/перезапуск и восстановление новым исполнителем по GitHub. Для экзамена нового агента исходный сервер разработки и старый чат недоступны; восстановление — из GitHub и заявленных независимых ресурсов, без чтения старых локальных файлов. Private runtime DB/keys в GitHub не публикуются; воссоздание не сохранённых секретов не обещается. Два каталога одного хоста или зелёные unit tests этого не заменяют.

Windows — следующий **обязательный** этап; прежние contracts/proof/fixtures и гарантии сохраняются, но native Windows не является gate первого Linux-пилота. Кандидаты remote-dev-system и vds02 ещё не имеют подтверждённой физической readiness/точного допуска. Ресурсы, custody SSH/TLS и scope требуют отдельного решения; VPN/Amnezia не менять.

M1/M2 и прежние опыты ниже сохраняют исторические составы и результаты. Текущее состояние — [handoff](handoff/START.md). Стратегию непосредственно утвердил владелец; эту документационную публикацию поручил архитектор по [6564431584](https://github.com/mdbm-code/ai-ecosystem-core/pull/7#issuecomment-6564431584), с уточнением authority [6564271952](https://github.com/mdbm-code/ai-ecosystem-core/issues/6#issuecomment-6564271952).

## 3. Что уже работает и где границы доказательств

M1 — обычная автономная Linux FCIA-dev, а не fixture: проверенный offline-комплект,
init/status, постоянные ID и lock, локальные Git-реестр и журнал, Naming Preflight,
резервирование и создание локальной синтетической заготовки. После перезапуска
сохраняются идентичность и результат. [Инструкция и ограничения](M1-DEV.md).

В исследовательской основе уже есть публикации реестра, подписи/полномочия,
долговечные поручения, pin исполнителя, обнаружение, mTLS, повторы и управляемые
обновления/откаты. Они проверены в своих лабораторных контекстах. Это не означает,
что все возможности включены в профиль M1-dev: у него пока нет сетевого enrollment,
смены выбранного lock или работающей федерации обычных dev-установок.

Настоящие локальные Git-операции есть. Реального GitHub-адаптера Naming нет:
исследовательский внешний этап использует fixture-хостер, а M1-dev оставляет
external и первый component commit ожидающими. Публикация исходников Core через
GitHub-коннектор не является таким адаптером.

Python допустим для будущих компонентов, но Python-runtime, OneCD Reader и MCP не
включены в M1. Создание/регистрация, проверка артефакта, подготовка runtime и
разрешённый запуск — разные стадии. Лимиты артефактов не повышаются без измерений.
UI, проекты 1С, модели и универсальный Tool Gateway не являются зависимостями M2.

## 4. Проверяемое определение первого релиза-пилота

Целевой первый пилот: две отдельно разрешённые Linux-установки на разных машинах входят в одну область владельца. Физический допуск пока не выдан.
Они создают тестовые компоненты по единой новой процедуре, работают локально без
связи и после её восстановления получают согласованный каталог с прежними ID.
Минимальный проверенный тестовый выпуск устанавливается и выполняет одну объявленную
межузловую операцию с сохранением поручения/результата при повторе и перезапуске.
CLI предоставляет явные запуск, состояние и остановку принадлежащих пилоту процессов.

Локальная заготовка, установленный артефакт и работающий компонент различаются.
Полный цикл создания не объявляется завершённым, пока внешний этап остаётся pending.
Для него нужен отдельный проверяемый путь связывания Naming с репозиторием,
предварительно созданным владельцем; автоматический GitHub create не требуется.
Проверенные provenance/digest и конкретные полномочия сохраняются на всех стадиях.

Два каталога на одном хосте — предварительный опыт, не запуск на двух машинах.
Первый пилот не требует UI, 1С, Python, marketplace, системного автозапуска или
универсального аудита всех инструментов. Его приёмка не означает production-готовность
для клиентских машин, гарантию exactly-once для внешних записей или миграцию всех
старых компонентов.

## 5. Предлагаемый маршрут

| Срез | Результат | Граница |
|---|---|---|
| M2: обычные dev-контексты и каталог | Две новые dev-установки в разрешённой пилотной области автономно регистрируют заготовки и обмениваются проверенными публикациями | Можно начать с двух root на одном Linux-хосте; не fixture и не физический релиз |
| Межузловое выполнение тестового компонента | Существующие очередь/исполнитель/обнаружение/транспорт связаны с dev-контекстом и проверенным тестовым выпуском; одна операция переживает обрыв и повтор | Узкий контракт Node-операции, без 1С/Python/UI; реальная привязка owner-created remote проверяется отдельным адаптером до полного цикла создания |
| Первый физический релиз-пилот | Два отдельных Linux-узла; настоящий компонент/GitHub L/R/C/D, каталог/ACK, работа, обновление/перезапуск и fresh GitHub recovery | Кандидаты remote-dev-system/vds02; readiness и exact physical approval отсутствуют |
| Следующий обязательный этап: Windows | Native Windows с прежними contracts/proof/fixtures и полными платформенными гарантиями | Отдельная приёмка; новые Windows работы пока не назначены |

После пилота — паспорт соответствия компонентов v1 и одна согласованная миграция.
Целевой порядок создания один: исследование кандидата → решение владельца →
назначение руководителя проекта → Naming → создание/проверки/приёмка.
Историческая _meta сохраняется; возврат к старой процедуре для новых компонентов
не является запасным автоматическим путём. Существующие проекты продолжают по
действующим назначениям до согласованного перехода. Массовой миграции сейчас нет.

### Предложение задания M2 и пять критериев

Использовать принятые Naming, журнал, Git-реестр, публикации/bundle и проверку состава.
Добавить проверяемые dev-адаптеры контекста, а не снять fixture-guard для любых путей.
Не перепроектировать принятую модель имён/ID/повторов.

1. Две новые обычные dev-установки имеют разные постоянные installation ID и явно
   разрешённое членство в одной области. Нет fixture=true, усыновления существующих
   каталогов или ручной подмены чужих identity/binding.
2. При отсутствии связи каждая создаёт свою синтетическую заготовку через Naming.
   Неверное имя отвергается до резерва/регистрации/каталога; повторы сохраняют ID.
3. После обмена обе видят обе записи с прежними ID и происхождением. Повтор публикации
   не даёт дублей, недопустимая публикация отвергается. Состояния R/C не изображаются
   успешными без реального подтверждения.
4. Прерывание, перезапуск и повтор сохраняют регистрации/журнал и чужие данные.
   Неизвестный результат проверяется с прежним ID. Состав фиксируется манифестом,
   проходят затронутые регрессии и независимое ревью.
5. При недоступном исходном сервере новый назначенный агент без истории чата получает
   опубликованную GitHub-точку, проверяет её полноту, восстанавливает состояние задачи,
   различает выполненные/неизвестные эффекты и определяет безопасное продолжение.
   Локальный комплект или один итоговый STATE этого критерия не заменяют.

## 6. Минимальное организационное условие до M2

Архитектору требуется подготовить короткий контракт включения установки в пилотную
область: источник принятой ревизии правил, субъект разрешения, источник domain ID,
проверка нового installation ID/членства, привязка к исходной истории реестра,
полномочия местного регистратора и писателей публикаций, отзыв и повтор включения.
M1 сейчас создаёт собственный domainId; одинаковый текст в JSON двух установок
не доказывает общее членство. Клонирование не переносит пост P000 или живую сессию.

До эффекта фиксируются задача/попытка, входная ревизия, устойчивый ID и основание
полномочий. После него — результат, доказательства либо UNKNOWN с способом сверки.
Публикация рабочей ветки не является приёмкой/merge, а новый чат не наследует
исключительное право записи автоматически.

Параллельно можно уточнять шаблон аудита кандидата, журнал решений владельца
«принят/отклонён» и паспорт соответствия старого компонента. Новые роли/процедуры
не выдаются за уже внедрённые; исследование кандидата не разрешает его создание.

## 7. Публикация шагов и восстановление

Оргполитика и инструкции должны одинаково действовать для Desktop, VSCode, CLI,
Claude Code, Codex, Kimi и местных моделей. Клиент не является источником истины.

Контрольная точка содержит ID проекта/задачи/попытки, ответственного и границы прав,
ревизии кода/контрактов, выполненные шаги, устойчивые ID операций, результаты,
неизвестные исходы, необходимые артефакты и следующий шаг. Состояние сохраняется
по ходу работ, а не только перед добровольным завершением чата.

| Состояние сохранения | Что можно утверждать |
|---|---|
| LOCAL_ONLY | Запись устойчива местно, внешнее сохранение не подтверждено; после потери диска может быть утрачена |
| PUBLICATION_UNKNOWN | Публикация начата, её исход неизвестен; проверить прежний commit/ID, не создавать новую операцию вслепую |
| PUBLISHED_CONFIRMED | Проверен точный remote SHA/состав; указаны сохраняемый объём и оставшиеся пробелы |

Пока сети нет, локальная работа продолжается. Неопубликованное не объявляется
сохранённым в GitHub. При возвращении связи изменения публикуются в пределах
разрешённой ветки/прав, без автоматического merge расходящихся историй.
Сообщение в чате, строка SHA или успешный локальный commit не заменяют проверки remote.

Для экзамена нового агента исходный сервер разработки и старый чат недоступны; восстановление — из GitHub и заявленных независимых ресурсов, без чтения старых локальных файлов. Private runtime DB/keys в GitHub не публикуются; воссоздание не сохранённых секретов не обещается. Из заявленных доступных ресурсов должны получаться необходимые код, документы и контрольные данные; проверяются происхождение и полнота. Ссылка только на /srv/ai-system/_tmp,
непереданные журналы или артефакты старой машины не позволяют поставить PASS.
Если нужный ресурс недоступен, фиксируются пробел и граница продолжения.

Требование не разрешает хранить секреты, рабочие базы, персональные данные или
скрытые рассуждения моделей в Git. Публикуется проверяемый журнал действий и безопасные
свидетельства; защищённые зависимости и их восстановление описываются отдельно.
Автоматический универсальный шлюз всех инструментов не является предпосылкой.

## 8. Ближайший шаг и неизвестное

Настоящая публикация не объявляет full/lint/product PASS и не разрешает повтор.

После технических gates предстоят точная готовность/допуск двух отдельных Linux-узлов и полный реальный цикл из раздела4. Windows остаётся обязательным следующим этапом; [slice1](deferred/windows-slice1/README.md) отложен без интеграции. UI frozen, ИнтеграцияС77 отдельно; main/PR3/архив/_meta/реальные узлы не меняются.
